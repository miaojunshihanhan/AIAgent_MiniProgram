# chat-v6 耗时排查记录

2026-10-20，在本机使用配置中的真实 Qwen 模型与现有材料索引测试。索引包含 45 份材料、378 个分块。没有修改或发布线上服务；微信网关、线上 COS 和真机素材加载时间尚未测得。

同一问题：新生儿喝奶后如何帮助排出吞入的空气？请给出要点和相关演示。

旧链路材料加载约 15 ms；一次模型请求等待约 8324 ms 后返回，且该次返回引用不一致，未得到可交付答案。旧代码允许最多 6 次模型请求，材料工具往返会串行增加等待；这次基线没有复现多轮调用，因此不将其当作多轮耗时对比或成功回答的提速比例。

新版真实模型 + 本地 HTTP 提交任务 + WebSocket 接收结果：

| 阶段 | 耗时 |
| --- | ---: |
| 创建任务持久化 | 1 ms |
| 索引加载 | 27 ms |

模型请求共 1 次，实际回答 270 字符，返回 7 项材料引用，其中 3 项媒体。另一次适配器直连测试首文字约 1.6 秒、总计约 7.2 秒。以上是少量本地样本，非线上 SLA，模型排队与网络会产生波动。

最大开销是模型生成，其次是首内容等待。已移除最多 6 轮的模型工具循环；后端一次准备预算内材料；精简系统提示词，默认 2–4 个要点、约 150–250 字；Qwen 默认关闭额外思考；SSE 生成后经 WebSocket 立即传送文字。按提示控制字数，不硬截断。

存储写入由逐阶段等待改为异步增量快照，最多一个快照在途，防止慢 COS 形成串行积压；最终完成状态仍在持久化成功后发送。断线仅查询同一任务，不重新请求模型。

## 部署后验证

确认 `/health` 为 `2026-10-20-chat-v7` 且 `streaming`、`singleModelCall`、`timings` 为 true。按同一 `requestId` 查看 `[timing]` 日志；每次普通提问应有一条 `[model] requesting`，其中 `calls=1 stream=true`。预设问题不调用模型。

小程序开发者工具查看 `[chat timing]` 的 `firstDisplayMs`、`totalDisplayMs`、`assetUrlMs`、`imageReadyMs`。若后端首字快、前端慢，比较云 WebSocket 是否正常，还是已回退快照；若 `job_create`/`job_finish` 慢，排查 COS 网络与权限；若 `firstTokenMs` 或 `generationMs` 慢，排查模型提供商排队、思考配置与输出长度。

本地重复诊断：在 backend 目录执行 `npm run profile:chat -- 你的问题`。每次执行会调用一次真实模型并产生相应费用；脚本只记录耗时和长度，不打印密钥、问题和回答正文。该脚本只测索引准备和模型阶段，不能替代微信真机测量。
